# Inventory, marks and edits: from a scan to a model you can talk about (2026-10-01)

The scan gives a mesh; the layout gives a plan. Neither knows what anything *is*. This phase adds the vocabulary:
every grill, fence run, sand pit and lawn becomes a named thing with a footprint, so "remove the grill" and
"the sand pit becomes lawn" are operations on named elements rather than on triangles.

Three kinds of thing change. Scan and extend stay as they are.

## Recording kind: marks

A **marks** recording is a list of items drawn on one 3D model in the app's full-view mesh editor. An item is a
point, a line or a polygon of 3D points **in that model's own coordinate frame**, with a class, an optional name,
note and material, and a provenance. Two roles share the kind:

| role | classes | meaning |
|---|---|---|
| `element` | wall, fence, window, door, stairs, area, tree, object | what is there |
| `edit` | remove, patch | what to change: `remove` names an inventory entity or outlines a region; `patch` outlines a region and carries a text prompt for what belongs there |

```
recording.json  kind "marks", source {"model": "model3d-1", "frame": "model3d-1"}
  items: [{id, role, cls, shape: point|line|polygon, points: [[x,y,z], ...], name, note, material, text,
           entity: "e12" | null, source: "human" | "accepted", at}]
```

`source.frame` is the coordinate frame the points live in: the scan that defined it. An edit publishes a model in
its parent's frame, so marks made on `model3d-1` stay valid on `model3d-2`; an extend publishes a new frame.

**Measurements on the mesh.** A measurement item may now be two 3D points instead of two pixels:
`{"source": "mesh", "model": "model3d-1", "a3d": [x,y,z], "b3d": [x,y,z], "meters": …}`. `measure_project.py` takes
them as constraints directly when the layout's model shares that frame, so every click lands.

## The inventory is a generated marks recording (changed 2026-10-03)

The user's call: marks and the inventory are the same kind of thing, a recording; one is drawn by a person, the other
generated by a run. So an identify run publishes a **marks recording** with `source.generated: true`, every entity as
an item (role `element`, `entity` = its id, source `generated`, plus confidence, area_m2, height_m, frames, color), and
the files below in the recording dir. A model page toggles the inventory and your marks on and off over the viewer.
Nothing is an asset here; the only assets are 3D models and site plans.

```
recording.json  kind "marks", source {"model", "frame", "generated_by": "r6", "generated": true, "metrics": {...}}, items [...]
entities.json   {"model", "frame", "levelled": <4x4 transform_preview matrix>, "est_scale",
                 "entities": [{id, cls, name, description, material, confidence, frames, faces, centroid, height_m*, outline, shape, review?}]}
faces.npy       int32 per face of dense/scene_dense_mesh_clean.ply: entity index, -1 = unlabelled
lift/label_faces.npy, labels.json   the label per face before clustering (the edit run uses them to tell ground from walls)
segments/       the named 2D masks per frame, so a later identify (prior = this recording) can re-lift them
inventory_map.png, thumb.jpg
```
`*` in model units until a layout applies its scale; `outline` is a 3D polyline/polygon on the mesh, which is what
the app draws over the preview and what becomes a mark when you accept an entity.

Dependencies between recordings and assets (2026-10-03): measurements marked on a video's frames depend on that video;
marks, inventories and mesh measurements depend on the model they were made on; an edited model depends on its parent.
Deleting something asks once, lists what depends on it, and deletes the lot. Runs are history and stay.

## Runs

| run | status | slots | stages | publishes |
|---|---|---|---|---|
| scan | unchanged | video | sfm, dense, landmarks, preview | 3D Model |
| extend | unchanged | 3D model, new footage | register, dense, landmarks, preview | 3D Model |
| **identify** | new | 3D model, prior inventory (optional, a generated marks recording) | segment, name, lift, entities, review, preview | a generated **marks recording** |
| layout | changed | 3D model, measurements, **marks** (yours and generated) | solve, ortho, trace, **annotate**, draw, preview | Site Plan |
| **edit** | new | 3D model, marks (yours with edit items, and the generated inventory) | select, cut, complete, preview | 3D Model |

### identify

*segment* runs SAM in automatic mode over a subset of the registered frames (no vocabulary; every region is a
mask). *name* draws the masks of a frame as numbered outlines and asks a vision-language model, once per frame, to
name each number: class from the taxonomy, a free description, a confidence (Set-of-Mark prompting). The model is a
run setting: a local Qwen2.5-VL through MLX, or a hosted model. *lift* casts every named mask's pixels through its
frame's camera onto the mesh (Open3D `cast_rays` returns the face index), and votes per face across frames: names
that agree across views win, one-off hallucinations lose. *entities* takes connected runs of faces with the same
winning label as instances, names each from the votes, and computes centroid, height, outline and footprint in the
levelled frame. *review* re-projects each entity into its best frame, outlines it on the photo and asks the model
whether it is one object and what it is; disagreements lower the confidence. *preview* draws the labelled map.

With a prior inventory in the slot, segment and name are skipped: the prior's named masks are re-lifted onto the
new mesh (minutes, not tens of minutes). That is how an inventory follows a model through an edit; the edit's
model lists the entities it removed, and their masks are dropped.

### layout, annotate stage

*annotate* merges the inventory's entities with the element marks into `elements.json` in plan coordinates
(metres, through `transform.json`). A mark linked to an entity replaces it; unlinked marks are added; entities
pass through as proposals with their confidence. When marks include walls or fences, they override the traced
walls on the drawing. *draw* puts every class on its own DXF layer (`WALLS`, `FENCES`, `WINDOWS`, `DOORS`, `STAIRS`,
`AREA_<MATERIAL>`, `TREES`, `OBJECTS`), adds a legend and a quantities table (areas, lengths, counts), and writes
the elements into `overlay.json` so the app draws and lists them. With neither slot filled, layout behaves as before.

### edit

*select* resolves each `remove` mark to faces: the entity's faces when the mark names one (plus the rim of ground
directly under its footprint, so the hole has a clean ground edge), else the faces whose centroid falls inside the
mark's polygon, grown to whole entities when the polygon covers most of one; structural faces (walls, fences, stairs,
windows, doors) are never taken unless they are the entity itself. A `patch` polygon takes only junk far from the
ground; a `patch` *point* ("patch here", from a right-click in a hole) takes nothing and says where to look. A ground
plane is fitted to the ring around each footprint. The selection is written as 3 cm voxels (the textured mesh shares
the clean mesh's faces) and as a region for the cloud. *cut* removes those faces from the clean mesh and the points
inside the region from the dense cloud. *complete* (Blender) cuts the textured mesh the same way, then finds the holes
on a 5 cm raster of the remaining faces (flood-filled from the footprint, or from the point), snaps the mesh's rim
vertices onto each hole's outline, triangulates the hole onto a surface fitted to that rim (constrained Delaunay with
interior points), and gives the patch a material textured from the surrounding ground at the right texel scale; the
first attempt, chaining boundary edges into loops, failed on photogrammetry rims (non-manifold, hundreds of tiny
loops) and was replaced on 2026-10-03. The cloud gets points sampled on the new triangles. *preview* clones the
parent's poses, database and measurements, re-renders the preview plan and exports the USDZ. The output is a 3D Model
with `derived_from` the parent and `frame` the parent's frame, plus `removed_entities`.

In the app, a right-click in Full View offers the edit directly: on an entity, Remove / Remove & Run Edit / Accept /
Reject; on a hole or bare ground, Patch Here / Patch Here & Run Edit; on one of your edit polygons, Run Edit Now. The
run takes the model, your marks and the newest inventory.

### Chains

"Site plan from video" becomes scan → identify → layout. "Clean up" is edit → identify (prior inventory) → layout.
A chained run may now wait for more than one run: any slot value `@r5` (in a single slot or inside a list slot) names
run r5's output, and the run starts when every run it waits for has published.

### The plan's structure (2026-10-03)

The user looked at plan r10: the orange wall lines were more accurate than the black boundary wherever they
differed (the stair groove, the bay-window indent, the narrow passage), and they wanted one line, not two; and they
wanted the areas they marked (sand pit, grass, brick, garden) to partition the yard, with a toggle between the outline
and that layout of the land, and windows, doors and fences marked as such.

So: the layout setting `boundary` (default `walls`) builds the plan on the wall-first boundary (perimeter walls chained
corner to corner, the ground's outline only where no wall was found; its own min edge is 0.4 m, so small jogs survive),
with `footprint` as the alternative; both are kept in `elements.json` / `overlay.json` under `boundaries`, and the app
switches between them. Wall segments that lie on the chosen boundary are not drawn again (`walls_interior` is what the
drawing shows in orange). Every boundary edge is classed `wall` / `fence` / `unknown` from the wall and fence elements
running along it (a person's marks weigh three times a generated entity) and drawn thick / ticked / dashed; windows and
doors are snapped onto the edge they sit on (`openings`) and drawn as a double line or a leaf with its swing. The land
use (`landuse`) partitions the chosen boundary: a person's areas first, the most specific (smallest) winning where they
overlap, then generated ground entities that are not minor, each clipped to the boundary and to what came before, and the
rest is "unassigned ground"; polygons carry holes. The PDF gains a third page (land use) and the DXF the layers
BOUNDARY_WALL, BOUNDARY_FENCE, BOUNDARY_ALT (off), OPENINGS and LANDUSE hatches. In the app the plan has an Outline /
Land use mode and a walls / footprint picker; your marks are always drawn as outlines, the inventory's entities only when
asked.

### Outer and inner (2026-10-05)

The user wants one black line drawing with measurements, in two versions. **Outer** is the boundary alone (walls first,
edge by edge, with its openings) and its dimensions. **Inner** adds the partition of the ground from the person's area
marks as the same black line, every side that is not the boundary dimensioned, each area named with its square metres,
and the person's other marks (trees, objects) as outlines. No colour fills on either; the traced wall lines (orange)
are off by default and the inventory's entities only appear when asked. The PDF pages are ortho, outer, inner; the DXF
carries the partition as dimensioned polylines on PARTITION. A marks recording's page shows the model with only that
recording's marks drawn on it (a generated inventory shows its entities), so a recording is legible on its own.

### annotate, precedence

Generated inventories come first, a person's marks override them: a mark linked to an entity replaces it, a mark with
`reject` drops it, and a person's area polygon drops every generated ground entity it covers by half or more. Small
(< 0.3 m²) or unsure (< 50 %) generated entities are kept as `minor`: listed, not drawn, not counted.

## The user story

1. Film and scan: rec1 → scan r1 → model3d-1.
2. Identify: r2 (model3d-1) → inventory-1: house wall, three fence runs, bay window, door, stairs, grill, bin,
   bike, sand pit, lawn, brick paving, two trees, a bush, each with a name and a confidence.
3. Correct and measure: full view of model3d-1; accept the walls and stairs, fix the fence that was called a wall,
   close the sand pit → marks rec3; two clicks on the patio edge plus the taped metres → measurements rec4.
4. Lay out: r3 (model3d-1, rec4, rec3, inventory-1) → site_plan-1 with legend and quantities.
5. Remove the clutter: edit marks rec5 (remove grill, bin, bike; patch the lawn hole, "lawn") → edit r4 → model3d-2.
6. Carry the inventory: identify r5 (model3d-2, prior inventory-1) → inventory-2.
7. Lay out again: r6 (model3d-2, rec4, rec3, inventory-2) → site_plan-2. Steps 5–7 are the "Clean up" chain.
8. Later: a design run on model3d-2 and inventory-2.

```
rec1 video ─► scan r1 ─► model3d-1 ─► identify r2 ─► inventory-1
                              │              │
   rec3 marks (elements) ─────┤              │
   rec4 measurements ─────────┼──────────────┼─► layout r3 ─► site_plan-1
                              │              │
   rec5 marks (edits) ────────┴──────────────┴─► edit r4 ─► model3d-2 ─► identify r5 (prior inventory-1) ─► inventory-2
                                                                 │                                             │
                                             rec3, rec4 ─────────┴─────────────────────────────────────────────┴─► layout r6 ─► site_plan-2
```

## Coordinates in the app's mesh editor

The preview USDZ is exported by Blender with `transform_preview.json` applied (levelled, Z up) and Blender's
orientation conversion (forward -Z, up Y). Verified on the noon backyard: a SceneKit world point `p` on the preview
maps to the levelled frame as `(p.x, -p.z, p.y)` and to the model's own frame through the inverse of
`transform_preview.json`'s matrix. A site plan's preview uses `transform.json` the same way. Marks and mesh
measurements are stored in the model frame, never in preview coordinates.

## Order of work

1. Marks recording kind and mesh measurements (schema, `measure_project.py`), the full-view mesh editor.
2. Identify as a run with the inventory asset; the editor shows entities as proposals.
3. Layout's marks and inventory slots and the annotate stage; elements on the DXF, PDF and in the app.
4. Edit: select, cut, complete; chains.
